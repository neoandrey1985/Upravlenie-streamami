# Управление стримами и командами — agent & contributor guide

Веб-приложение для agile-планирования по двухнедельным спринтам. Полиглот-стек:
`frontend/` (самодостаточный SPA на ванильном JS в одном `index.html`),
`backend-java/` (Spring Boot REST API + PostgreSQL, Flyway-миграции),
`analytics-python/` (FastAPI — движок метрик), `nginx` (reverse-proxy),
всё поднимается через `docker-compose.yml`.

Это **форк** «Управления кросс-функциональной командой» (`upstream` = github.com/neoandrey1985/Planirovanie,
точка ветвления — тег `fork-base`) с уровнем «Стрим → Команда»: у каждой команды свои данные.

## Стримы и команды — устройство и правила

- **Схема БД на команду.** Первая команда (`t1`) живёт в `public`, остальные — в `team_<id>`; их миграции —
  те же `db/migration` из базового проекта. Платформенные таблицы (`org_streams`, `org_teams`, `org_memberships`)
  — только в `public`, миграции в `db/platform` (своя история `platform_schema_history`). **Не клади платформенные
  таблицы в `db/migration`** и не занимай там номера версий — они приходят из upstream.
- **Контекст команды:** заголовок `X-Team-Id` (или `?team=`) у `/api/state`, `/api/tasks`, `/analytics/*`;
  доска — `/ws/board?team=`. `AuthInterceptor` проверяет доступ и ставит `TenantContext`.
- **Доступ:** ADMIN — всё; пользователь без назначений — общая роль на всех командах; иначе — максимум из роли
  в команде и роли в её стриме (`OrgService.effectiveRole`, то же в `analytics-python/app/org.py`).
- **Код форка** держи отдельно: `com.planirovanie.org`, `db/platform`, блок «Стримы и команды» в `index.html`.
  Общий код меняй минимально — так `git merge upstream/main` проходит без конфликтов.
- **Уровень стрима** (меню «Стрим»): свои данные — документ стрима (`/api/org/streams/{id}/doc`, локально
  `streamapp:stream:<id>`, в коде `SDOC`, `sdocSave()`); сводки считаются функциями команды (`compute`,
  `sprintRisk`, `sayDo`) по данным каждой команды через `withState()`. Истории фич пишутся в бэклог команды
  (`teamAddTask`), связь — `feature.links`. Роль в стриме: STREAM-назначение; участник команды — только просмотр.
- **Фронтенд:** данные команды — ключ `stKey()` (`streamapp:<id>`), данные-«базы» команды — `tkey()`;
  не пиши `localStorage('streamapp…')` напрямую. Смена команды — только `switchTeam()`.

Подводные камни:
- Hibernate выбирает схему при **открытии** сессии: не переключай `TenantContext` внутри `@Transactional`
  (`OrgService` специально без транзакции; используй `TenantContext.callAs`).
- Тесты (H2, без Flyway) создают схему команды копией `public` (`SCRIPT NODATA`); путь PostgreSQL+Flyway
  проверяет только CI-шаг «Stack smoke test» (создание команды на живом стеке).
- `migrate()` добавляет демо-эпики только при наличии демо-задачи `T-01` — пустые команды остаются пустыми.
- Миграции `db/migration` с V13 — собственные (проекты развиваются раздельно, merge из upstream не делается);
  они применяются и к public, и к схеме каждой команды (V13 — `tasks.stages`, `params.stage_roles`).
- «Мой профиль»: привязка учётной записи к участнику — `public.app_users.member_name` (платформенная миграция V4,
  одна на все команды); `PUT /api/auth/me` и `/api/auth/me/password` доступны любой роли (свой профиль).

Перенос исправлений из базового проекта: `git fetch upstream && git merge upstream/main`
(или `git cherry-pick <sha>`), затем `make test`.

## Build / run

```bash
make up            # собрать и запустить весь стек на http://localhost:8090
make build         # только собрать образы
docker compose down
```

Локальный предпросмотр только фронтенда: `python -m http.server 4190 --directory frontend`.

## Test — регрессия по всему функционалу

Один прогон покрывает всё приложение. **Запускай перед каждым коммитом; CI гоняет то же на каждый push/PR.**

```bash
make test            # Java (Spring Boot + H2) + Python + frontend e2e — полная регрессия
make test-java       # backend:  cd backend-java && mvn -B -ntp test   (MockMvc, H2)
make test-python     # analytics: python analytics-python/tests/test_compute.py
make test-frontend   # frontend:  python tests/frontend/run_e2e.py     (Playwright, всё приложение)
```

- **Frontend e2e** — [`tests/frontend/run_e2e.py`](tests/frontend/run_e2e.py): поднимает статический сервер,
  запускает headless Chromium, проверяет метрики, EDA, экспорт Excel/PPTX (в т.ч. регресс на «битый файл»),
  Kanban, релизы, доску, миграции и права. См. [`tests/frontend/README.md`](tests/frontend/README.md).
- **Backend** запускается в песочнице только через `mvn -o test` (MockMvc); живой Tomcat/RANDOM_PORT в песочнице
  не стартует — не полагайся на него в тестах.

## Правило: новый функционал → автотесты (обязательно)

Любой PR, добавляющий или меняющий поведение, обязан обновить тесты в том же изменении:

1. **Новый раздел приложения** (пункт в `NAV` в `frontend/index.html`) покрывается **автоматически** —
   smoke-цикл в `run_e2e.py` сам обнаруживает все разделы из `NAV` и проверяет, что каждый рендерится без
   ошибок консоли. Отдельный код теста писать не нужно.
2. **Новая логика** (расчётный путь, экспорт, автоматизация, новая модель данных, серверный эндпоинт) требует
   **отдельного теста**:
   - фронтенд — добавь блок `case('<область>: <поведение>', t_fn)` в `run_e2e.py` по образцу соседних;
     проверяй форму данных и диапазоны, а не точные значения демо-данных, чтобы тест не «краснел» при смене seed;
   - backend — добавь тест в `backend-java/src/test/...` (MockMvc);
   - analytics — расширь `analytics-python/tests/`.
3. Прогони `make test`. Красный тест — блокер, чинится причина, а не тест.

Регрессия по определению покрывает весь функционал: `make test` — это и есть регрессионный набор.

## Code style / соглашения

- Фронтенд — единый `frontend/index.html` (без сборки): правь его напрямую. Разделы = группы в `NAV`,
  контейнеры `#v_<id>`, рендер через `views()`/`setView()`; вся запись данных проходит через `save()`
  (гейт `PERM.canEdit`). Версия — `APP_VERSION`, история — `CHANGELOG` (голова changelog обязана совпадать с версией; это проверяет тест).
- Помощник (чат-бот) **самообучается**: его база знаний (`buildKB()` в IIFE чата) строится на каждой загрузке
  из самого приложения — `NAV` (разделы/блоки), живые `h1`/`.lede` каждого `#v_<id>`, массив `TOUR` и `CHANGELOG`.
  Поэтому новый/переименованный раздел и изменённое описание попадают в ответы помощника **автоматически**, без
  правок бота. Чтобы раздел хорошо находился по синонимам, добавь ключевые слова в карту `AKA`; живые метрики
  раздела — отдельным `if(/regex/)` в `reply()` выше секционного фолбэка. Покрытие всех разделов из `NAV`
  проверяет e2e-тест `assistant: knows every NAV section` (через хук `window.assistantAsk`/`assistantKB`).
- После изменения приложения обновляй сопутствующие документы (руководства, презентация, инструкция по
  развёртыванию) и перезаписывай скриншоты, затем пушь в GitHub.
- Ветка по умолчанию — `main`; CI обязателен к прохождению до merge.
